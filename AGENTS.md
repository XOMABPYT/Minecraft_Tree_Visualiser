# AGENTS.md — Minecraft Tree Visualiser

Инструкции для ИИ-агентов и разработчиков, работающих над проектом.
Перед любыми изменениями прочитай этот файл целиком.

## 1. Что это за проект

Визуализатор деревьев поиска внутри Minecraft. Поддерживаемые структуры:

| id в протоколе | Структура |
|---|---|
| `avl` | AVL-дерево |
| `rb` | Красно-чёрное дерево |
| `treap` | Декартово дерево (treap) |
| `splay` | Splay-дерево |
| `btree` | B-дерево |

Как это работает для пользователя:

- ключ добавляется командой в чате (`/tree insert 42`), можно добавить сразу
  `n` случайных ключей (`/tree random 10`);
- ключ удаляется **выстрелом из лука** в блок узла;
- тип отображаемого дерева переключается командой (`/tree view treap`), при этом
  показывается то же множество ключей, представленное другой структурой;
- при наведении взгляда на узел в actionbar выводятся его подробности;
- анимации нет: после каждой операции дерево перерисовывается мгновенно.

## 2. Архитектура

```
Minecraft-клиент (игрок)
        │  localhost
        ▼
Сервер Paper + плагин (Java, папка Plugin/)
        │  stdin/stdout, одна строка JSON = одно сообщение
        ▼
Backend (C++17, папка Backend/) — вся логика деревьев и раскладки
```

Принципы:

- **Вся логика — в C++.** Деревья, их состояние и расчёт координат узлов живут
  в Backend. Плагин ничего не знает о том, как устроены деревья.
- **Плагин — «тупой» рендерер и источник событий.** Он принимает команды и
  попадания стрел, пересылает их в Backend, получает готовую раскладку и рисует
  её. Плагин не должен содержать логику, специфичную для конкретного типа дерева:
  всё, что нужно показать (цвет, подписи, подробности), приходит из Backend.
- **Все пять деревьев живут параллельно.** Каждая операция (`insert`, `random`, `delete`)
  применяется ко всем деревьям сразу, а `view` лишь меняет, какое из них
  отображается. Переключение не перестраивает деревья.
- Плагин сам запускает Backend как дочерний процесс через `ProcessBuilder` и
  завершает его при выключении.

Файлы деревьев лежат прямо в корне `Backend/`, по паре `.h`/`.cpp` на дерево.
Их имена и расположение выбрал автор: не переименовывай и не перемещай их,
даже ради единообразия (например, `SplayTree.h` при `SplayTree.cpp`). Весь код
инфраструктуры кладётся в `Backend/src/`, а не в корень `Backend/`.

Структуру внутри `src/` можно уточнять по мере роста проекта, но разделение на
`Backend/` и `Plugin/` и файлы деревьев автора неизменны.

## 4. Границы ответственности — ВАЖНО

Автор проекта сам пишет алгоритмы деревьев. Это учебная цель проекта.

**Агентам ЗАПРЕЩЕНО:**

- писать, дописывать или «исправлять» реализации деревьев в файлах автора
  (`Backend/AvlTree.*`, `Backend/RBTree.*`, `Backend/Treap.*`,
  `Backend/SplayTree.h`, `Backend/SplayTree.cpp`, `Backend/BTree.*`):
  вставка, удаление, повороты, балансировка, splay, split/merge, разбиение
  и слияние узлов B-дерева и т.п.;
- подсказывать готовый код алгоритмов деревьев, если автор об этом прямо не попросил;
- менять публичный интерфейс дерева (`ITree`) без согласования с автором.

**Агентам РАЗРЕШЕНО:**

- весь Java-плагин (`Plugin/`);
- C++-инфраструктура: `main.cpp`, протокол и JSON, раскладка (`layout/`),
  хранилище деревьев (`world/`), интерфейс и снимок дерева (`core/`), CMake;
- тесты, в том числе тесты, проверяющие инварианты деревьев автора
  (сбалансированность AVL, свойства КЧД, свойство кучи у treap, свойства B-дерева,
  корректность in-order обхода);
- ревью кода деревьев: если тест или ревью нашли ошибку в файлах деревьев,
  **опиши проблему** (где, на каком входе и почему ломается), но не исправляй её;
- заглушки (stub) деревьев для тестирования инфраструктуры — только в тестах
  или в явно помеченном временном файле в `Backend/src/`, например простое
  несбалансированное BST, чтобы плагин можно было проверить до готовности деревьев.

Если задача требует изменений в файлах деревьев, остановись и спроси автора.
Агент может только подключить эти файлы к сборке в `CMakeLists.txt`.

## 5. Backend (C++)

### Технологии

- Стандарт **C++17**: без `std::format`, концептов, `ranges` и прочего из C++20.
- Сборка **CMake**; зависимости подключаются через `FetchContent`:
  - [nlohmann/json](https://github.com/nlohmann/json) — JSON;
  - [GoogleTest](https://github.com/google/googletest) — тесты.
- Сборка:
  ```
  cmake -S Backend -B Backend/build -DCMAKE_BUILD_TYPE=Debug
  cmake --build Backend/build
  ctest --test-dir Backend/build --output-on-failure
  ```

### Ключи

- Тип ключа — `std::int64_t` (`using Key = std::int64_t;`).
- Дубликаты запрещены: повторная вставка существующего ключа ничего не меняет
  и возвращает ошибку `duplicate_key`.
- **Случайные ключи** (команда `random`) генерирует Backend, а не плагин, и
  вставляет одни и те же ключи во все пять деревьев. Ключи выбираются
  равномерно из диапазона `[min, max]` среди тех, которых ещё нет в деревьях,
  и вставляются в порядке генерации: порядок важен, от него зависит форма
  деревьев. ГСЧ — `std::mt19937_64` с настраиваемым seed, отдельный от ГСЧ
  приоритетов treap.

### Интерфейс дерева (граница между кодом автора и инфраструктурой)

Каждое дерево автора (`AvlTree`, `RBTree`, `Treap`, `SplayTree`, `BTree`)
реализует общий интерфейс. Ориентировочный вид
(уточняется вместе с автором, менять только по согласованию):

```cpp
class ITree {
public:
    virtual ~ITree() = default;
    virtual bool insert(Key key) = 0;      // false, если ключ уже есть
    virtual bool erase(Key key) = 0;       // false, если ключа нет
    virtual TreeSnapshot snapshot() const = 0;
};
```

`TreeSnapshot` — независимое от реализации описание текущей формы дерева:
узлы с их ключами (один ключ у бинарных деревьев, несколько у B-дерева),
упорядоченный список детей, цвет и набор подробностей для показа. Раскладка и
протокол работают **только со снимком** и никогда не лезут во внутренности деревьев.

`snapshot()` обязан быть `const` и не менять дерево. Это особенно важно для splay:
просмотр, наведение и перерисовка не должны его перестраивать.

### Особенности отдельных деревьев

- **Treap.** Приоритет генерируется случайно при вставке ключа и далее не меняется.
  ГСЧ — `std::mt19937_64` с настраиваемым seed: в тестах seed фиксирован, чтобы
  результат был воспроизводимым. Приоритет показывается в подписи узла.
- **Splay.** Структура меняется только при `insert` и `delete`, отдельной команды
  поиска нет. Никакие служебные операции (снимок, наведение, рендер) не должны
  вызывать splay.
- **B-дерево.** Порядок (минимальная степень `t`) — константа в коде, по
  умолчанию `t = 3`. Командой не настраивается.
- **КЧД.** Цвет узла передаётся в поле `color` (`red` / `black`).
- **AVL.** В подробности узла стоит передавать высоту и баланс.

### Раскладка (layout)

- Считается в C++ по снимку дерева. Результат — целочисленные координаты в
  **условной сетке**: `x` — колонка, `depth` — уровень (корень = 0). Перевод в
  координаты мира делает плагин.
- Бинарные деревья: на старте `x` = порядковый номер узла в in-order обходе.
  Позже можно перейти на компактную раскладку (Reingold–Tilford), формат
  ответа при этом не меняется.
- B-дерево: узел занимает `keys.length` соседних клеток начиная с `x`.
  Листья укладываются слева направо с промежутком, родитель центрируется над
  своими детьми.
- Узлы не должны перекрываться: это стоит покрыть тестами раскладки.

### Правила ввода-вывода

- **stdout — только протокол.** Одна строка = один JSON-ответ, после каждого
  ответа обязательно `std::flush` (или `std::endl`).
- Все логи и отладка — **только в stderr**. Плагин перенаправляет stderr в лог сервера.
- Некорректный запрос не должен ронять процесс: вернуть ответ с ошибкой и
  продолжить работу.

## 6. Протокол Plugin ⇄ Backend

Транспорт: stdin/stdout дочернего процесса, UTF-8, одна строка JSON на сообщение.
Модель «запрос → ответ»: в каждый момент времени выполняется не больше одного
запроса, плагин ждёт ответа и только потом отправляет следующий.

### Запросы (Plugin → Backend)

```json
{"id": 1, "cmd": "insert", "key": 42}
{"id": 2, "cmd": "random", "count": 10, "min": 0, "max": 999}
{"id": 3, "cmd": "delete", "key": 42}
{"id": 4, "cmd": "view",   "tree": "treap"}
{"id": 5, "cmd": "clear"}
{"id": 6, "cmd": "state"}
```

- `insert` / `random` / `delete` применяются ко **всем** деревьям.
- `random` вставляет `count` новых случайных ключей из `[min, max]`. Если
  свободных ключей в диапазоне меньше `count`, ничего не вставляется и
  возвращается ошибка `range_exhausted`. В успешном ответе дополнительно есть
  поле `"inserted": [17, 503, ...]` — вставленные ключи в порядке вставки.
- `view` меняет активное дерево.
- `clear` очищает все деревья.
- `state` возвращает текущую раскладку без изменений (нужен при старте и
  перезапуске плагина).

### Ответ (Backend → Plugin)

Ответ на любую команду содержит полную раскладку активного дерева:

```json
{
  "id": 1,
  "ok": true,
  "tree": "rb",
  "nodes": [
    {
      "id": 7,
      "keys": [42],
      "x": 3,
      "depth": 0,
      "color": "black",
      "label": ["42"],
      "info": {"height": "3", "subtree": "5"}
    }
  ],
  "edges": [
    {"from": 7, "to": 8, "slot": 0}
  ]
}
```

- `id` узла уникален в пределах ответа; между ответами он может меняться.
- `keys` — ключи узла по порядку (у бинарных деревьев ровно один).
- `color` — один из фиксированного набора: `white`, `red`, `black`, `gray`,
  `blue`, `green`, `yellow`. Плагин сопоставляет его с блоком (шерстью или бетоном).
- `label` — строки подписи над узлом. Например, у treap: `["42", "p=17"]`.
- `info` — подробности для actionbar при наведении (строки «ключ: значение»).
- `slot` у ребра — номер ребёнка (у B-дерева номер промежутка между ключами).

Ошибка:

```json
{"id": 1, "ok": false, "error": "duplicate_key", "message": "Key 42 already exists"}
```

Коды ошибок: `duplicate_key`, `key_not_found`, `unknown_tree`,
`range_exhausted`, `bad_request`.

Протокол — общий контракт. Любое изменение формата делается одновременно в
Backend и Plugin, и этот раздел обновляется в том же коммите.

## 7. Plugin (Java, Paper)

### Технологии

- Серверное ядро **Paper**, актуальная версия 1.21.x на момент начала разработки.
  Точная версия фиксируется в `build.gradle.kts` и README; клиент Minecraft
  должен быть **той же версии**.
- **Java 21** (или та версия, которую требует выбранный Paper).
- Сборка **Gradle** (Kotlin DSL) + плагин
  [`xyz.jpenilla.run-paper`](https://github.com/jpenilla/run-task) для локального запуска:
  ```
  cd Plugin
  ./gradlew build        # собрать jar плагина
  ./gradlew runServer    # скачать Paper, положить плагин и запустить сервер
  ```
- Команду `/reload` для перезагрузки плагина не использовать: после изменений
  перезапускать сервер.

### Команды

| Команда | Действие |
|---|---|
| `/tree insert <key>` | вставить ключ во все деревья |
| `/tree random <n> [min] [max]` | вставить `n` случайных ключей во все деревья |
| `/tree view <avl\|rb\|treap\|splay\|btree>` | показать другое дерево |
| `/tree clear` | очистить все деревья |

Для `/tree random`: если `min` и `max` не указаны, они берутся из `config.yml`
(`random.min`, `random.max`, по умолчанию `0` и `999`). Плагин проверяет, что
`n >= 1` и `n <= random.max-count` (по умолчанию `100`), иначе слишком большое
дерево не поместится и будет долго перерисовываться. После вставки плагин
пишет в чат список вставленных ключей из поля `inserted`.

Новые команды добавляются только по согласованию с автором.

### Рендеринг

- Дерево — вертикальная «стена» в плоскости XY при фиксированном Z. Точка
  привязки (`origin`) и шаги сетки (`spacing-x`, `spacing-y`) задаются в `config.yml`.
- Перевод координат: `worldX = origin.x + x * spacingX`,
  `worldY = origin.y - depth * spacingY`.
- **Ключ узла = настоящий блок** (шерсть или бетон по полю `color`). Блок нужен и
  как мишень: стрелы не попадают в display-сущности, у них нет хитбокса.
  У B-дерева отдельный блок на каждый ключ.
- **Подпись** — `TextDisplay` над блоком: billboard `CENTER`, полупрозрачный фон,
  `setPersistent(false)`.
- **Рёбра** — `BlockDisplay`: тонкий вытянутый блок, повёрнутый от родителя к
  ребёнку (поворот через кватернион в `Transformation`).
- Перерисовка: удалить все ранее созданные блоки и сущности (плагин хранит
  ссылки на них), затем построить заново по ответу.
- При выключении плагина всё созданное удаляется, а процесс Backend завершается.

### События

- **Удаление выстрелом:** `ProjectileHitEvent`. Учитывать только стрелы,
  выпущенные игроком и попавшие в блок. Плагин хранит словарь
  «координаты блока → ключ», по нему находит ключ и отправляет `delete`.
  Стрелу после попадания удалить (`arrow.remove()`).
- **Наведение:** периодическая задача (раз в несколько тиков) делает
  `player.rayTraceBlocks(...)`. Если игрок смотрит на блок узла, в actionbar
  выводится `info` этого узла. Наведение работает только с последним полученным
  ответом и **не отправляет запросов** в Backend.

### Потоки — частая ошибка

- Мир (блоки и сущности) можно менять **только из главного потока сервера**.
- Чтение stdout Backend — в отдельном потоке. Разобранный ответ передаётся в
  главный поток через `Bukkit.getScheduler().runTask(plugin, ...)`.
- stderr Backend читается в отдельном потоке и пишется в логгер плагина.
- Если процесс Backend упал или не ответил за разумный таймаут, плагин пишет
  об этом в чат и лог и не зависает. Желательна команда или механизм перезапуска.

## 8. Локальный сервер для разработки

- `./gradlew runServer` создаёт сервер в папке `Plugin/run/`.
- При первом запуске нужно принять `eula.txt` (`eula=true`).
- Рекомендуемые настройки `server.properties`: `level-type=flat`,
  `gamemode=creative`, `spawn-protection=0`, `spawn-monsters=false`.
- В игре: `/gamerule doDaylightCycle false`, `/gamerule doWeatherCycle false`.
- Права на команды выдаются в консоли сервера: `op <ник>`.
- Подключение: «Сетевая игра» → «Прямое подключение» → `localhost`.
- Путь к бинарнику Backend указывается в `config.yml` плагина
  (по умолчанию `../Backend/build/<имя бинарника>` относительно корня проекта).

### Окружение (macOS)

На момент создания файла Java и CMake на машине **не установлены**:

```
brew install --cask temurin@21
brew install cmake
```

## 9. Стиль кода и соглашения

- **Язык:** комментарии, сообщения коммитов и документация — на русском.
  Идентификаторы (имена классов, функций, переменных) — на английском.
- Комментарии пишутся только там, где код сам не объясняет ограничение или причину.
- C++: RAII, без голых `new`/`delete` в инфраструктуре (`std::unique_ptr`),
  без глобального изменяемого состояния; предупреждения `-Wall -Wextra` включены.
- Java: стандартные соглашения Java, без лишних зависимостей кроме Paper API.
- Каждая новая функция инфраструктуры C++ (протокол, раскладка, хранилище
  деревьев) покрывается тестами GoogleTest.
- Перед коммитом: Backend собирается и `ctest` проходит, `./gradlew build` проходит.
